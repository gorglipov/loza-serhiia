## Тестове оформлення в каталозі LOZA

Картку `grape-demo` додано безпосередньо в наявний каталог `index.html`, перед списком сортів. Вона використовує кольори, типографіку й оформлення магазину. На смартфонах блок переходить в одну колонку; елементи керування мають висоту щонайменше 48 px.

Покупець обирає від 1 до 5 штук, бачить попередню суму (500 грн × кількість) і натискає **Купити**. Після відповіді API показуються номер, фактична сума із сервера та статус `pending`. Реальна оплата не виконується, форма не запитує банківські дані та не звертається до Monobank.

### Файли інтеграції

- `index.html` — нова картка та підключення двох локальних ресурсів. Решта розмітки, 107 сортів, кошик і наявний код магазину збережені.
- `demo-order.css` — стилі картки, адаптивне компонування та видимий фокус клавіатури.
- `demo-order.js` — розрахунок попередньої суми, запит API, стани очікування/успіху/помилки й повторні спроби.
- `functions/api/orders/create.js` — чинний API, доповнений безпечними повторними запитами, перевіркою формату JSON та відповідями без кешування.
- `.gitignore` — локальні секрети та файли Wrangler не потрапляють до Git.

Сторінка `/order-demo`, маршрутизація `_routes.json` та всі інші Pages Functions залишені як у репозиторії. Інтеграція не замінює старе оформлення замовлень і не змінює наявні інтеграції Telegram, Нової пошти чи Monobank.

### API та D1

Використовується той самий `POST /api/orders/create` і Cloudflare D1 binding **DB**. У Cloudflare Pages цей binding має посилатися на вже підключену базу `grape-orders` у потрібному середовищі (Production або Preview).

Таблиця `orders` має наявні стовпці `id`, `amount_kop`, `status`; для `id` потрібен `PRIMARY KEY` або `UNIQUE`. Нові таблиці, стовпці та міграції не додаються. Ідентифікатор бази й секрети не потрібно записувати в статичні файли.

Запит з браузера:

```http
POST /api/orders/create
Content-Type: application/json
Idempotency-Key: <UUID одного замовлення>

{"product":"grape-demo","quantity":2}
```

Остаточну ціну визначає серверний каталог: `50000` копійок за штуку. Значення 500 грн у браузері потрібне лише для попереднього розрахунку. Сервер перевіряє товар і цілу кількість 1–5, ігнорує передані клієнтом ціну/суму/статус та зберігає суму в копійках зі статусом `pending`.

Приклад відповіді нового замовлення (`201`):

```json
{
  "success": true,
  "orderId": "TEST-<UUID одного замовлення>",
  "amount": 1000,
  "currency": "UAH",
  "status": "pending",
  "testOnly": true
}
```

У відповіді `amount` передається у гривнях. Підсумок у картці береться саме з цієї відповіді.

Під час запиту кнопка й кількість блокуються. Ключ запиту та кількість тимчасово зберігаються в `sessionStorage`, щоб повторити запит після обриву зв’язку або перезавантаження тієї самої вкладки. Повтор з тим самим ключем і кількістю повертає те саме замовлення (`200`); інша кількість з тим самим ключем дає `409`. Нове замовлення після успіху створюється окремою кнопкою. Старі клієнти, зокрема `/order-demo`, можуть надсилати запит без цього необов’язкового заголовка, як раніше.

Помилки: `400` — некоректні дані, `403` — стороннє походження запиту, `415` — не JSON, `503` — binding недоступний, `500` — помилка бази. Внутрішні помилки D1 не повертаються клієнту. `MONO_TOKEN`, `MONO_WEBHOOK_KEY` та інші секрети залишаються на сервері.

### Публікація через GitHub

Зміни підготовлено в гілці `codex/integrate-demo-orders` від актуального `main`. До GitHub потрібно передати перелічені файли інтеграції та цей README, зберігши решту файлів репозиторію. Поточний Cloudflare Pages проєкт продовжує використовувати налаштований D1 binding `DB`; новий `wrangler.toml` із вигаданими ідентифікаторами не потрібен.

Після публікації Git-гілки можна відкрити pull request у `main` і використати Cloudflare Pages Preview з його власним налаштованим binding `DB`. Запити тестового оформлення створюють справжні рядки `TEST-*` у підключеній D1, але не запускають оплату.
