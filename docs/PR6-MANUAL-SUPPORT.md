# PR №6: ручна наявність, назви та підтримка

## Каталог

Усі 107 сортів, PDF-джерело, характеристики, ціни, пошук, фільтри й дизайн без фото збережені. Наявність визначає тільки ручний перемикач адміністратора. Замовлення, повтор запиту та скасування **не змінюють** його.

Складський облік вимкнено. `products.stock`, `order_stock_reservations` та старі журнали повернень збережені як історичні дані сумісності. Новий код їх не змінює, не показує як залишок, не використовує для доступності або ліміту покупки. Умовні залишки не встановлюються.

Окремі ліміти: **1–20 лоз сорту, до 100 лоз загалом, до 20 різних сортів у замовленні**. Їх перевіряють браузер, сервер і D1-тригер. Ціна та ручна наявність повторно перевіряються всередині транзакції оформлення.

Для купівлі потрібні ввімкнений перемикач і підтвердження саме поточної ціни. Сам імпорт PDF або ввімкнення наявності не підтверджує ціну. Без ціни показується «Ціну уточнюйте», покупка вимкнена. Власник окремо вказав **залишити вже підтверджені 84 ціни** у Preview; 23 сорти без ціни не продаються. Міграція 0008 не скидає й не підтверджує цін.

## Редагування назв і CSV

«Товари → Змінити назву» дозволяє виправити назву (2–160 символів). Вона також редагується у повному редакторі та CSV. Код товару, ціна, підтвердження, наявність, характеристики й початковий PDF-рядок зберігаються. Є аудит і перевірка версії; застарілий редактор не перезапише нові дані. Каталог/пошук/нові замовлення отримують нову назву, старі `order_items.product_name` не змінюються.

CSV — **14 колонок без stock**. `name` — назва, `available` — ручна наявність (0/1), `price_confirmed` — явне підтвердження власника (0/1). Завантажуйте актуальний шаблон; старий 15-колонковий файл відхиляється без змін даних.

## Підтримка

Кнопки є вгорі, внизу магазину та в кошику. Обов'язкові:

- Причина: оформлення, доставка/відділення, каталог/ціна/назва/наявність, статус замовлення, технічна проблема або інше.
- Telegram `@username` (5–32 латинські літери/цифри/підкреслення) або український телефон, що нормалізується до +380XXXXXXXXX.
- Повідомлення 10–2000 символів.

`POST /api/support/create`: JSON, UUID `Idempotency-Key`, перевірка Origin/Content-Type, обмежений розмір тіла, Turnstile з окремим action `loza_support`, honeypot, 3 запити/хв на HMAC IP. Один ключ прив'язаний до нормалізованих даних і не створює дубль. Контакт/повідомлення не зберігаються у localStorage/sessionStorage; знімок невизначеного запиту є лише в пам'яті вкладки для повтору.

Таблиці `support_tickets`, `support_admin_actions`, `support_outbox`, `support_notification_actions` приватні. Публічна відповідь містить тільки номер і підтвердження прийняття. Публічних списків або пошуку звернення немає.

`/admin → Підтримка`: приватний список, пошук за номером/контактом, повідомлення, контакт для відповіді, статуси «Нове / В роботі / Вирішено», версії та історія змін. Усі маршрути перевіряють на сервері Access JWT, ADMIN_EMAILS і CSRF для змін; відповіді no-store, SQL параметризований, дані відображаються як текст.

Telegram використовує існуючі серверні секрети й глобальний перемикач сповіщень. Він отримує **лише номер звернення та причину**, без контакту або тексту повідомлення. Звернення й outbox записуються атомарно, надсилання відбувається після commit. Помилка Telegram не скасовує звернення. Підтверджені тимчасові відмови повторюються з backoff/`retry_after`; невизначена доставка стає `uncertain` і потребує свідомого рішення адміністратора. Захищений повтор має аудит.

Для фонових повторів без активної сторінки потрібно оновити окремий **Preview** Cron Worker із `workers/telegram-retry.js`. Production Worker цією роботою не розгортається. Нових секретів/ботів/webhook не потрібно. Форма не приймає файлів або платіжних реквізитів; прямі контакти Сергія доступні у разі недоступного Turnstile.

## Міграція та розгортання Preview

0007 уже застосована до Preview, тому її історичний файл не переписано. Нова **0008_manual_catalog_support** прибирає автоматичне списання/повернення, відновлює ручні тригери, додає таблиці підтримки. Існуючі таблиці не перебудовуються, записи замовлень/позицій, ціни/підтвердження, банківські дані, Telegram та аудит зберігаються.

Binding `DB` Preview звірено: він відрізняється від Production. Команда застосування (вже виконана тільки в Preview):

```powershell
npx.cmd wrangler d1 execute DB --remote --config .wrangler/manual-v8-preview.toml --file migrations/0008_manual_catalog_support.sql
```

Локальний ігнорований Git конфіг повинен посилатися саме на UUID Preview. Код вимагає маркер 0008: спочатку міграція, потім новий Preview. Після цього не запускайте старі 0004/0005/0007 окремо — вони можуть відновити попередній режим.

Production зараз не змінюється. Після окремого дозволу, якщо там тільки 0002–0005, потрібно підготувати атомарний імпорт **0007 + 0008 одним файлом**, щоб не залишити проміжний складський режим. 0006 потрібна лише для таблиць моніторингу й не вмикає живий банк. Спершу резервна копія/Time Travel і перевірка актуальної схеми, потім міграції та звірка даних, тільки після цього дозволені Merge і деплой.

## Перевірки

Збірка Pages Functions успішна. **62/62 тести без пропусків** на справжньому Worker/Miniflare D1: ручна наявність усіх 107 сортів, незалежні ліміти 20/100, відсутність списання/повернення, збереження старих назв/джерела PDF, CSV, мобільний інтерфейс, приватна підтримка та повтори Telegram, Access/CSRF/секрети, спільний моніторинг PR №5 та вимкнена оплата. Міграції перевірено на збереженій фактичній DDL Production із синтетичними приватними даними, включно з повторним 0008 і FK.

Тести не використовують живий банк або реальний бот. Публічний POST у живому Preview потребує Turnstile власника; агент CAPTCHA не обходить. Результат перевірки розгорнутого Preview і репетиції на Preview D1 наведено в PR №6.

У живій Preview D1 застосовано 0008 та звірено контрольні суми початкових таблиць: усі записи незмінні, FK коректні, 107 сортів, 84 підтверджені й доступні ціни, 23 без ціни. Окрема транзакційна репетиція успішно створила два тестові замовлення по 20 одного сорту, скасувала їх, перевірила незмінність наявності/історичної кількості/версії товару й статус/аудит підтримки. Після перевірки прибрано тільки створені тестові рядки; контрольні суми всіх початкових рядків знову збігаються. Реальні Telegram-повідомлення не надсилалися.
