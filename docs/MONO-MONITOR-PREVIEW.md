# LOZA: моніторинг надходжень monobank — Preview

Дата: 22.10.2026. Гілка `codex/mono-monitor-preview`, база — актуальний `main`
`3d66206e5ecb6fadde3cd87d239ab378b2b36b16` після злитого PR №4.
Production не змінювався. Реальні банківські запити та приймання платежів не активовані.

## 1. Результат перевірки чинного коду

- `MONO_TOKEN` використовується тільки на сервері. Раніше `/api/mono/api-check`
  викликав `personal/client-info` за спільним `MONO_WEBHOOK_KEY` у заголовку.
  Це був діагностичний запит, він не перевіряв надходження й не мав Access-захисту.
- `/api/mono/webhook` перевіряє секретний URL key, приймає `StatementItem` і робить
  `INSERT OR IGNORE` у `mono_events`. Файл webhook та його URL не змінено.
- `mono_events` має transaction/account ID, суму, валюту, description, hold та час
  отримання події. Час банківської операції й авторитетна перевірка там відсутні.
  Такий рядок не доводить надходження: webhook key не є підтвердженням виписки.
- Таблиця `mono_events` не змінена і не перебудована. Новий модуль не підвищує
  довіру до неї без окремого авторизованого читання виписки.
- Старий `/api/mono/api-check` у цій гілці закритий серверним Access JWT і CSRF.
  Навіть авторизованому адміністратору він повертає `MONO_LIVE_DISABLED` і не
  викликає банк. Попередній сценарій із `X-Admin-Key` більше не працює; заміна —
  розділ «Надходження» в адмінпанелі Preview. Це навмисне закриття старого probe.

Наявність конфігурації, без значень:

| Поле | Preview | Production |
| --- | --- | --- |
| `MONO_TOKEN` | false | true |
| `MONO_WEBHOOK_KEY` | false | true |
| `TELEGRAM_BOT_TOKEN` | true | true |
| `TELEGRAM_CHAT_ID` | true | true |

Секрети не змінювались і не виводились. Наявність Production-токена не активує
новий модуль; він не використовується жодним доступним маршрутом синхронізації.

## 2. Межа між тестом і живим банком

**Ця версія працює тільки на синтетичних даних.** Робочий URL тесту:

`https://codex-mono-monitor-preview.loza-serhiia.pages.dev/admin`

Авторизація — наявний Cloudflare Access, серверна перевірка підпису/issuer/AUD,
адміністративний email allowlist, CSRF, точний Origin, rate limit і no-store.
Сервер дозволяє fixture-режим тільки для цього іменного Preview alias та локальних
тестових адрес. Хешові deployment URL теж вимкнені: вони можуть належати Production.
Публічного API зі списком транзакцій або можливістю передати токен/рахунок немає.

`server/mono-statement.js` містить підготовлений адаптер офіційної виписки:
фіксований HTTPS host, `X-Token`, явно вибраний account, Unix from/to, заборона
переходу за redirect, timeout 8 с, обмеження розміру, валідація полів і очищення
помилок. Період обмежений 2682000 секунд; запити розділені щонайменше хвилиною.
Джерело цих API-обмежень — [офіційна документація monobank](https://api.monobank.ua/docs/).

`server/mono-bank-readonly.js` готує зв’язок наявних webhook-підказок із цією
випискою. Глобальний D1 lock спільний для рахунків, зберігає cooldown навіть після
помилки та враховує `Retry-After`. Немає маршруту, Cron handler або env-перемикача,
який викликав би цей адаптер із робочими секретами. Він перевірений тільки із
підставним transport у локальних тестах. Увімкнення потребує окремого рішення,
перевірки дозволеного сценарію та наступної зміни коду.

## 3. D1 і перевірка

Адитивна міграція: `migrations/0006_mono_monitor.sql`, **після 0005**, без повтору
старих міграцій. Вона створює тільки нові таблиці:

| Таблиця | Призначення |
| --- | --- |
| `mono_monitor_transactions` | Внутрішній UUID, bank transaction ID, account hash, сума в копійках, валюта, Unix час, hold, стан перевірки, джерело, час перевірки |
| `mono_monitor_sync_lock` | Спільний gate частоти й lease від паралельних запитів |
| `mono_monitor_runs` | Адміністратор, час, стан, очищений код помилки й підсумок перевірки |
| `mono_monitor_settings` | Окремі сповіщення модуля, за замовчуванням вимкнені; оптимістична версія |
| `mono_monitor_actions` | Ідемпотентні й журналювані зміни налаштувань/повтори |
| `mono_monitor_notifications` | Окрема durable черга, унікальна за transaction reference |
| `mono_monitor_fixture_orders` | Виключно навчальні замовлення; не додаються до `orders` |

Дублікати транзакцій відсікаються за `(account_ref, transaction_id)`, повідомлень —
за `transaction_ref`. Повтор синхронізації не створює новий order/event. Зберігання
пакетне з JSON-bound SQL і підготовленими параметрами; довільний SQL не приймається.
Дані одного узгодження й постановка сповіщень записуються одним D1 batch.

Стани:

- `unverified` — є лише підказка webhook, достовірного часу операції може не бути;
- `verified` — позитивна UAH операція без hold знайдена у виписці;
- `held` — банк ще утримує кошти, збігів/сповіщень немає;
- `mismatch` — сума або валюта webhook не збігається з випискою; зберігаються
  авторитетні значення виписки, потрібна ручна перевірка;
- `not_found` — підказка не знайдена **в запитаному періоді**, це не доказ
  відсутності коштів за весь час;
- `excluded` — списання, нуль або інша валюта, не UAH надходження.

На екрані fixture-операції чітко позначені як тестові,
`verifiedByBank: false`: синтетична виписка не видається за справжнє зарахування.
Неповний/потенційно обрізаний результат не використовується як негативний доказ.
500 рядків позначаються як можливо неповне вікно; більше 500 або понад 1 МБ
відхиляються. Автоматичного обходу всієї історії зараз немає.

Імена контрагентів, IBAN, PAN, податкові номери, баланс, descriptions/comments
із відповіді банку не додаються до нової таблиці. Старі записи `mono_events`
залишаються в попередньому вигляді, їх очищення/строк зберігання — окрема політика.
У відповідях браузеру навіть raw bank ID/account hash замінені внутрішнім UUID.

## 4. Збіги із замовленнями

Сума, валюта та час дають лише список можливих кандидатів: замовлення створене
не більш ніж за 72 години до операції, допускається 5 хвилин різниці годинника.
Показуються максимум 20 кандидатів, є ознака додаткових. Виконані/скасовані й
занадто старі замовлення виключені. Немає автоматичного прив’язування, статусу
«оплачено», зміни `orders`, резервування або списання наявності.

У Preview fixture-кандидати беруться **лише з окремої навчальної таблиці**:
MONO-DEMO-A/B на 500 грн і MONO-DEMO-C на 100 грн. Це дозволяє перевірити
неоднозначний збіг, не торкаючись наявних замовлень покупців. Реальний алгоритм
відбору з `orders`/`order_checkout` перевірений на синтетичній локальній D1.
Часткові оплати, комісії, розбиті/об’єднані перекази і доказ платника не визначаються.

## 5. Telegram

Окреме налаштування модуля початково вимкнене; також враховується чинний глобальний
перемикач Telegram. Ввімкнути можна лише через захищену адмінпанель, з явним
попередженням про надсилання тестових повідомлень.

Текст містить суму, час, скорочений внутрішній reference і стан перевірки,
без банківських реквізитів, опису/імені контрагента та контактів покупця.
Fixture-повідомлення починається з **«ТЕСТ LOZA · синтетичне надходження»**.
У чергу допускаються тільки придатні перевірені надходження; дубль не додається.
Перед відправкою придатність перевіряється знову.

Відомі 429/5xx від Telegram повторюються з відкладенням, до 8 спроб. Timeout,
втрата відповіді або прострочений lease дають `uncertain`: автоматичного повтору
немає, щоб не створити дубль. Для ручного повтору потрібне явне підтвердження.
Не можна гарантувати exactly-once доставку через зовнішній Bot API.

Помилка Telegram не скасовує ні перевірену транзакцію, ні замовлення. Чинні
Telegram webhook і токени не змінено. Окремий Cron Worker доповнений обробкою
нової черги й сумісний з D1 без 0006, але не розгортається цим PR. Без нього
повтори запускаються наступною синхронізацією або кнопкою адміністратора.

## 6. Перевірка у Preview

0006 застосована **тільки до окремої Preview D1**; її ID звірений з Pages Preview
binding і відрізняється від Production. 110 товарів, 2 наявні замовлення, 2 позиції,
0 legacy `mono_events`, глобальні налаштування й черга Telegram збережені.
Production-міграцій не було. Для іншого ізольованого Preview після 0005:

```powershell
npx.cmd wrangler d1 execute DB --remote --config .wrangler/mono-monitor-preview.toml --file migrations/0006_mono_monitor.sql
```

Локальний конфіг не входить у Git і має вказувати саме на окрему Preview D1.
Не запускайте його для Production. Нових секретів для тесту додавати не потрібно.

1. Відкрити іменний URL гілки `/admin`, увійти дозволеним Access акаунтом.
2. Обрати **Надходження → Перевірити тестові надходження**.
3. Очікувано: 7 транзакцій — 2 перевірені тестові надходження, 1 hold,
   1 розбіжність, 1 не знайдена у виписці підказка, 2 виключені операції.
4. Надходження 500 грн має два можливі навчальні збіги. Не повинно бути кнопки
   автоматичної оплати. Чинні замовлення/залишки не змінюються.
5. Повторне натискання раніше хвилини дає 429. Після хвилини кількість рядків
   і сповіщень лишається сталою. Повтор одного UUID ідемпотентний.
6. Telegram за замовчуванням вимкнений. Якщо власник хоче надіслати **реальні
   повідомлення з тестовими даними**, увімкнути перемикач і натиснути
   «Надіслати заплановані тести». Мають прийти два повідомлення з позначкою ТЕСТ.
7. В інкогніто admin API вимагає Access; підроблений заголовок email/старий
   `X-Admin-Key`, запит без CSRF або з чужим Origin не дає доступу.

Автоматизовані перевірки використовують підставні Access/Turnstile/банк/Telegram,
реальні банківські транзакції не читаються і реальному боту не пишуть.
**53/53 тести пройшли, 0 failed, 0 skipped.** Pages build і окремий Telegram
Worker dry-run успішні; сканування доданих до Git файлів не виявило секретів.
Команди повторення:

```powershell
npx.cmd wrangler pages functions build --outfile .wrangler/admin-worker.js
node --test tests/access-configuration.test.mjs tests/admin-preview.test.mjs tests/catalog-csv.test.mjs tests/production-migrations.test.mjs tests/mono-statement.test.mjs tests/source-secrets.test.mjs tests/telegram-retry.test.mjs
```

Потрібні Miniflare та Playwright/Edge; шляхи задаються `LOZA_MINIFLARE_MODULE` і
`LOZA_PLAYWRIGHT_MODULE`. До тестів входять браузер 390/1440 px, невірні JWT/CSRF,
конкурентні дублікати, неправдиві/некоректні webhook, помилки/redirect/429 банку,
розбіжності, різні рахунки, неповна виписка, секрети й невизначена доставка.

### Фактичний результат розгорнутого Preview

Cloudflare Preview build успішний, основний коміт `ac60d26`. Через наявний
дозволений Access-сеанс відкрито `/admin`, виконано синтетичну синхронізацію
і переглянуто два навчальні збіги 500 грн. Повтор протягом хвилини відхилений
з 429. Read-only перевірка D1 підтвердила:

- 7 рядків / 7 унікальних bank references, усі `data_source=fixture`;
- 2 verified, 1 held, 1 mismatch, 1 not_found, 2 excluded;
- рівно 2 повідомлення queued, attempts=0; сповіщення модуля залишені вимкненими;
- 2 старі замовлення/2 позиції, 110 товарів, 0 legacy mono_events,
  2 повідомлення старої Telegram-черги й 7 старих записів аудиту збережені;
- Production deployment досі `3d66206`, жодної Production-міграції/публікації немає.

Реальних банківських запитів або тестових повідомлень робочому боту під час
цієї перевірки не було. Telegram перевірений підставними відповідями; реальну
доставку власник може перевірити окремою явною дією з кроку 6.

## 7. Що потрібно погодити перед будь-яким живим запуском

1. З monobank/Universal Bank: дозволений тип рахунку, мету обробки надходжень,
   допустимість цього серверного personal API сценарію й умови зберігання даних.
   Токен персонального API сам по собі не є дозволом приймати комерційні платежі.
   [Офіційна документація API](https://api.monobank.ua/docs/) розрізняє персональне
   використання та API провайдерів послуг; тут не збираються токени покупців.
2. Допустиму правову модель продажів і відповідний рахунок. Особистий рахунок
   не слід використовувати для підприємницьких операцій: це прямо пояснює
   [ДПС з посиланням на п. 24 Інструкції НБУ №162](https://if.tax.gov.ua/media-ark/news-ark/print-1050692.html).
   Погодження банку не скасовує вимог законодавства. За потреби обрати інший
   дозволений банком спосіб приймання платежів, без обходу обмежень.
3. Явно вибраний рахунок/валюту, мінімальні права й ротацію серверного токена,
   приватність логів webhook URL (query key не повинен потрапляти у debug logs),
   строки зберігання/видалення фінансових даних і коло адміністраторів.
4. Окремо перевірити живий read-only адаптер із банком, відновлення після пропусків,
   paging/межі історії, навантаження, Cron, моніторинг помилок і план відкату.
5. Окремий PR/дозвіл на увімкнення та Production-міграцію. Поточний PR не вмикає
   live-режим навіть після Merge, але **Merge зараз не виконується**.

Цей модуль не визначає платника за сумою, не гарантує відсутності повернення/
сторнування і не підтверджує комерційну допустимість платежу. Номер, картка,
IBAN чи додаткові реквізити покупця не збираються для цієї перевірки.
