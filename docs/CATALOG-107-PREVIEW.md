# LOZA PR №4: каталог і ручна наявність

## Дані каталогу

Збережені всі 107 сортів та характеристики з PDF «Каталог лози винограду
2026–2027»: назва, смак, дозрівання, колір, вага ягід, форма, морозостійкість.
У джерелі 84 ціни з колонки «Лоза» та 23 порожні ціни, 28 явних позначок кишмишу.
Ціни у D1 — у копійках; назви/ціни/характеристики не вигадані. Оригінальний
знімок із номером сторінки/рядка збережений у `product_catalog.source_json`
та `server/catalog-source.json`; SHA-256 PDF:
`94ef2e033480691a9b1162a5e825f48b0d5671a3a3936e2e165bddbeeb138a01`.

Картки компактні, без фотографій і заглушок, з пошуком та фільтрами за кольором,
дозріванням, ціною, кишмишем. Характеристики з PDF потребують перевірки власником,
доки він не поставить відповідну позначку в редакторі.

## Ручна наявність: міграція 0005

- У `/admin` → «Товари» біля кожного сорту є перемикач
  **«В наявності / Немає в наявності»**. Він також є у редакторі товару.
- Кількість у штуках вводити не потрібно. У старому полі `products.stock`
  для сумісності зберігається **20 для сортів у наявності**, інакше 0.
  Це умовне значення: воно не лімітує сумарні замовлення й не списується.
- Наявність — окремий прапорець у `product_availability.in_stock`, незалежний
  від ціни. Можна позначити наявним сорт без ціни: купівля залишиться вимкненою.
- Додати до кошика можна лише сорт у наявності з додатною, підтвердженою
  для конкретної суми ціною. За відсутньої ціни показується **«Ціну уточнюйте»**.
- Якщо сорту немає, картка показує «Немає в наявності» й вимкнену кнопку.
  Підтверджена ціна у такої картки зберігається.
- Створення замовлення, відправлення, виконання й скасування не змінюють
  наявність або умовну кількість. Старі замовлення, позиції та історичний журнал
  повернень збережені; повторного повернення кількості немає.
- Кількість у конкретному замовленні залишається 1–5 для кожного сорту,
  до 20 різних сортів у кошику. Це правило замовлення, а не складський облік.

### Публічний API

`GET /api/products` повертає `inStock` — ручну наявність, `priceConfirmed` та
`available` — дозвіл купівлі з урахуванням ціни. Старий атрибут `stock` залишено
для сумісності як 20/0, інтерфейс його не показує і не використовує як ліміт.

`POST /api/cart/quote` та `POST /api/orders/create` перевіряють ручну наявність
і поточну підтверджену ціну на сервері. SQL-тригер повторно перевіряє їх у момент
запису замовлення. Сума та знімки позицій обчислюються в одній транзакції D1;
запис замовлення не змінює товари. Якщо сорт вимкнено після додавання в кошик,
оформлення повертає 409 без створення замовлення/сповіщення.

### Захищений API адміністратора

`POST /api/admin/products/<id>/availability`, JSON:

```json
{"version": 3, "inStock": true}
```

Потрібні перевірений Cloudflare Access JWT адміністратора, CSRF, точний Origin,
JSON та UUID у `Idempotency-Key`. Оптимістична версія захищає від перезапису змін
іншого адміністратора. Повтор того самого запиту ідемпотентний, у тому числі після
наступного редагування товару. Перемикання записується в `admin_audit_log` з
попереднім і новим станом. Приватні відповіді мають `Cache-Control: no-store`.

Редактор повного товару також приймає ручну наявність через `available`; клієнт
не може призначити числовий залишок: сервер і SQL самі виставляють 20/0.
Наявність не змінює ціну, її підтвердження або характеристики.

## CSV без кількості

Завантажте свіжий CSV: «Товари» → «Завантажити CSV». UTF-8 BOM, `;`, усі 107
сортів. Старий формат зі `stock` більше не приймається: завантажте новий шаблон.

| Колонка | Значення |
|---|---|
| `product_id`, `version` | Код і версія зі свіжого експорту; код не змінювати |
| `name` | Назва сорту |
| `price_uah` | Ціна у гривнях до двох десяткових знаків; порожньо = уточнюється |
| `price_confirmed` | 1 — підтверджено конкретну ціну, 0 — ні; порожню ціну підтвердити не можна |
| `available` | **Ручна наявність**, 1 або 0, незалежно від ціни |
| `taste`, `ripening`, `color` | Смак, дозрівання, колір |
| `kishmish` | 1 — позначка кишмишу, 0 — без позначки |
| `berry`, `shape`, `frost` | Вага ягід, форма, морозостійкість |
| `characteristics_confirmed` | 1 після перевірки власником, інакше 0 |

14 колонок, без фото та кількісного залишку. Імпорт: вибрати файл → «Перевірити
файл» → переглянути дані → «Застосувати імпорт». Він підтримує до 107 рядків / 250 КБ,
коректні лапки/коми/крапки, атомарний відкат, аудит та повтор без дублів.
Застарілі версії відхиляються. Створення замовлень не змінює версію товару,
а ручне редагування чи перемикання наявності змінює її.

## Застосування до Preview D1

Цей PR потребує **дві міграції** після вже чинної 0003:

1. `migrations/0004_catalog_107.sql` — каталог/ціни/джерело/CSV.
2. `migrations/0005_manual_availability.sql` — ручна наявність без списання.

0004 і 0005 вже застосовані до Preview. Повторно їх запускати для публікації
цієї гілки не потрібно. Не запускайте
старі міграції після 0005: для повторного виконання використовуйте тільки 0005.
Вона не скидає налаштовані ручні прапорці, ціни або підтвердження.

Cloudflare → Workers & Pages → `loza-serhiia` → Settings → Bindings → **Preview**.
Звірте ID `DB`: він має відрізнятися від Production. Відкрийте саме цю Preview D1
→ Console й виконайте файл 0005 цілком, без додавання `BEGIN`/`COMMIT`.
Після міграції розгорніть цю гілку у Preview і оновіть браузер.

Альтернатива CLI з локальним `.wrangler/catalog-preview.toml`, у якому binding `DB`
вказує виключно на перевірений ID окремої Preview-бази:

```powershell
npx.cmd wrangler d1 execute DB --remote --config .wrangler/catalog-preview.toml --file migrations/0005_manual_availability.sql
```

Перевірки:

```sql
SELECT version FROM loza_store_migrations WHERE version IN('0004_catalog_107','0005_manual_availability');
SELECT COUNT(*) FROM product_availability; -- 107
SELECT COUNT(*) FROM products p JOIN product_availability a ON a.product_id=p.id
 WHERE p.stock<>CASE WHEN a.in_stock=1 THEN 20 ELSE 0 END; -- 0
SELECT name FROM sqlite_schema WHERE type='trigger' AND name IN
 ('loza_checkout_reserve_v2','loza_stock_return_once'); -- жодних рядків
PRAGMA foreign_key_check; -- жодних порушень
```

Початкові ручні статуси успадковуються з поточної наявності; товари автоматично
не оголошуються наявними. Три демотовари залишаються архівними, історія замовлень,
`mono_events`, Access, monobank та Telegram не змінюються. Реальна оплата вимкнена.

**Production не мігрувати, не розгортати і PR не зливати без окремого дозволу.**

node --test tests/access-configuration.test.mjs tests/admin-preview.test.mjs tests/catalog-csv.test.mjs tests/production-migrations.test.mjs tests/source-secrets.test.mjs tests/telegram-retry.test.mjs

DDL без рядків покупців, підписаний тестовий JWT, заглушки Turnstile/Telegram
і Edge 320/390/1440 px; реальний бот не викликається.

повтори/конфлікти; замовлення сумарно понад 20 штук без списання; скасування без
повернень; повторна перевірка вже заповненого кошика та SQL-гонка з відкатом.
